# Better Auth comparison after passkeys and MFA

Checked 2026-09-20 against current official Better Auth documentation (site labels latest version 1.7.5) and `auth/README.md`. This is a feature/documentation comparison, not an independent security audit. Enterprise identity integrations, SSO, SAML and SCIM are excluded. Better Auth plugin capabilities below require installation/configuration; they are not all defaults.

## Assessment

Howdy now covers the normal consumer account lifecycle: email/password/provider login, verified email changes, account deletion, guarded provider unlinking, passkey management, TOTP/delivered MFA, recovery codes, remembered devices, and session management. These are no longer major missing feature categories. Howdy remains narrower in client integration, configurable user experience, consumer login choices and operational tooling. Coverage alone cannot establish equivalent security assurance or maturity. Local evidence: [auth README](../auth/README.md).

## Verified remaining differences

| Area | Better Auth | Howdy and implication |
| --- | --- | --- |
| Passkeys | Optional plugin provides registration/login/list/rename/delete, conditional browser autofill, configurable RP ID and authenticator selection, WebAuthn extensions and opt-in pre-session registration through application user-resolution hooks. [Passkey docs](https://better-auth.com/docs/plugins/passkey) | Core lifecycle implemented. No conditional autofill, passkey-first signup, parent-domain RP choice, extension configuration or Expo support. Exact-origin/hostname RP, discoverable credentials and user verification required. Better Auth's default resident-key/user-verification preferences are more permissive, but configurable. |
| MFA | Optional plugin offers TOTP, callback-delivered OTP, backup codes and trusted devices; customizable TOTP digits/period, OTP lifetime/storage and recovery-code generation. Trusted devices renew their 30-day trust on successful sign-in. Account-wide failed-verification lockout spans challenges/factors by default. [2FA docs](https://better-auth.com/docs/plugins/2fa) | Everyday lifecycle now present. Format/lifetime knobs are fixed, trust expires after a fixed 30 days, starter UI shows a manual key rather than QR. Howdy also has persistent per-account guessing protection; this is not unique to Howdy. |
| MFA enforcement | Default enforcement gates email/password, username/password and phone/password credential endpoints. Social, passkey, magic-link and other passwordless logins need custom hooks if they must also demand MFA. [2FA enforcement](https://better-auth.com/docs/plugins/2fa#sign-in-with-2fa) | Howdy gates all its primary methods for enrolled users. This is a meaningful stricter default, not proof of overall superior security. |
| Client SDK | Framework clients for React, Vue, Svelte and others provide consistent methods/hooks, session revalidation options and SSR hydration. [Client docs](https://better-auth.com/docs/concepts/client) | Howdy has Gleam headless APIs, JSON endpoints and minimal starter pages, but no equivalent typed reactive browser/mobile SDK. App teams implement transport/state glue themselves. |
| Sessions | Configurable rolling expiry; default seven-day sessions refreshed after one-day update age. Optional cookie-cache/stateless patterns. Separate multi-session plugin switches accounts within one browser without signing out. [Session docs](https://better-auth.com/docs/concepts/session-management), [multi-session plugin](https://better-auth.com/docs/plugins/multi-session) | Howdy lists/revokes sessions and supports external storage; has absolute expiry and optional idle timeout, no rolling renewal, cookie-cache or same-browser account switching. Multiple devices are already supported; do not call that missing. |
| Social providers | Built-in adapters include Apple and Discord, among many others. Generic OAuth plugin supports explicit endpoint configuration or OIDC discovery and custom user-info mapping. [Apple](https://better-auth.com/docs/authentication/apple), [Discord](https://better-auth.com/docs/authentication/discord), [generic OAuth](https://better-auth.com/docs/plugins/generic-oauth) | Howdy ships Google/GitHub/Facebook/Entra and an internal provider-construction seam, not a supported public extension contract. It lacks the ready-made breadth; adding another adapter requires implementation. Generic enterprise identity work can remain deferred. |
| Extra consumer login methods | Optional username, phone-number, anonymous-account, magic-link and email-OTP plugins. [Username](https://better-auth.com/docs/plugins/username), [phone](https://better-auth.com/docs/plugins/phone-number), [anonymous](https://better-auth.com/docs/plugins/anonymous), [magic link](https://better-auth.com/docs/plugins/magic-link), [email OTP](https://better-auth.com/docs/plugins/email-otp) | Howdy's email authentication is a pasted long opaque token exchanged by POST. It is passwordless email authentication, but not clickable magic links or short-code email login. Delivered second-factor OTP is not a phone/email primary-login feature. |
| API credentials | Optional API-key plugin provides creation, verification, updating, deletion and permission checks. Optional JWT plugin supplies JWT/JWKS capabilities; device authorization serves devices/CLI login. [API keys](https://better-auth.com/docs/plugins/api-key), [JWT](https://better-auth.com/docs/plugins/jwt), [device authorization](https://better-auth.com/docs/plugins/device-authorization) | Howdy's bearer sessions exist, but are not scoped long-lived API keys or a JWT issuer. These are relevant if apps expose automation/integration APIs, not prerequisites for ordinary browser login. |
| Abuse controls | Core HTTP rate limiter supports memory, database, secondary storage or atomic custom storage. Optional CAPTCHA and breached-password-check plugins. [Rate limiting](https://better-auth.com/docs/concepts/rate-limit), [CAPTCHA](https://better-auth.com/docs/plugins/captcha), [HIBP](https://better-auth.com/docs/plugins/have-i-been-pwned) | Howdy has process-local HTTP limits plus shared database protections for email/password/MFA. Missing shared backend for the general HTTP limiter and packaged CAPTCHA/HIBP integrations. Do not imply all Howdy limits are process-local or that password strength checks are absent. |
| Administration | Optional admin plugin exposes permission-checked user/session operations and impersonation through server and client APIs. OpenAPI plugin generates API schema/reference support. [Admin](https://better-auth.com/docs/plugins/admin), [OpenAPI](https://better-auth.com/docs/plugins/open-api) | Howdy provides trusted headless suspend/resume/revoke and RBAC APIs, audit records, but no equivalent packaged admin HTTP/client layer or impersonation. Admin plugin should not be described as a built-in hosted dashboard. |

## Account lifecycle nuance

Better Auth already supports email changes, deletion hooks/verification and ownership-checked unlinking; unlinking the sole account is denied by default, with a configurable escape hatch. Howdy has closed these main categories with deliberately narrower recent-authentication policies. Its email change verifies the new mailbox but does not independently confirm through the old mailbox; Better Auth offers old-email confirmation configuration. App-owned deletion cleanup is still an application responsibility in both designs. [User/account docs](https://better-auth.com/docs/concepts/users-accounts), [Howdy account lifecycle](../auth/README.md#email-changes-account-deletion-and-provider-unlinking).

## Priorities suggested by this comparison

1. Validate and harden the newly added cryptographic paths with real browser/authenticator interoperability and independent review. Howdy pins prerelease `glasslock 1.0.0-rc1` and uses internal metadata parsing APIs; its README explicitly states no independent audit in this work. Better Auth's passkey plugin uses SimpleWebAuthn. This is a dependency assurance difference to investigate, not evidence of a specific flaw. [Howdy scope](../auth/README.md#scope-compared-with-better-auth), [Better Auth passkey implementation](https://better-auth.com/docs/plugins/passkey).
2. Improve everyday UX: local QR rendering, passkey conditional autofill and useful reauthentication/recovery affordances. Then client SDK/session integration if Howdy targets custom frontends.
3. Add shared general HTTP rate limiting for multi-instance deployment; consider pluggable CAPTCHA/breached-password checking when application needs justify them.
4. Choose subsequent breadth from product demand: Apple/other consumer providers, short email codes, rolling sessions, or scoped API keys. Avoid implementing every plugin merely to inflate parity.

No numeric security score or parity percentage is justified by this documentation review. The fair conclusion is substantial core lifecycle parity, with Better Auth still ahead in ecosystem breadth, client convenience and configuration range.
