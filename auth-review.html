Two notes on what was not changed

The module size. auth.gleam is 938 lines and I stopped short of breaking it up. The operations that remain there all read the fields of the opaque Auth, so moving them means either giving those fields up or passing four of them into every call, and moving public functions into new modules would change the API for the sake of a line count. What could move cleanly — origin and address canonicalisation, which depend on nothing — has moved. I would rather leave this one visible than spend the package's API on it.

The concurrency cap. I went to measure this before implementing it and found the finding's premise was wrong, so there is nothing to fix; the measurement is in the table above. That also means the route limiter is doing the load-shedding work here, so it stays worth configuring for a real deployment.

Summary

This is a careful, security-literate module — noticeably better than most hand-rolled auth. The fundamentals are right: 256-bit random tokens stored only as digests, atomic single-use challenge exchange, Argon2id with a dummy-hash path for unknown users, __Host- HttpOnly cookies, exact Origin checks on cookie writes, and rejection of ambiguous credentials. The weaknesses are not broken crypto; they are abuse/denial-of-service edges in the throttling design, missing account lifecycle features (no password change/reset), a contention problem in the SQLite lock, and operational rigidity (nothing is configurable; the schema fingerprint has no escape hatch; a vendored C crypto dependency blocks publishing).

Security — 7.5 / 10

What is done well

  • Tokens are 32 bytes from crypto.strong_random_bytes; only SHA-256 digests are stored for challenges and sessions, so a database leak does not yield usable sessions. A test asserts raw tokens are never persisted.
  • Challenge exchange is a single DELETE … RETURNING inside a transaction — a token can mint at most one session even under concurrency (and there is a test for exactly that).
  • Password login performs the same Argon2 work for unknown, email-only and suspended accounts via a startup dummy hash; hashing runs outside the DB transaction; the credential is re-checked and the row locked afterwards so suspension or a concurrent change cannot issue a stale session.
  • Argon2id parameters are pinned explicitly (19 MiB, t=2, p=1 — the OWASP baseline), the encoded prefix is verified, and a known-answer test guards the vendored fix. Catching the upstream ARGON2_VERSION 13 vs 0x13 bug is impressive diligence.
  • Cookies: __Host- prefix, Secure, HttpOnly, SameSite=Lax, Path=/. HTTPS is enforced except on loopback. The origin is never inferred from Host or forwarded headers.
  • CSRF: cookie-authenticated non-GET requests require an exact single Origin; JSON endpoints require application/json; requests carrying both a cookie and a bearer header are rejected; duplicate cookies/headers are rejected.
  • Registration is off by default, re-checked at exchange time, and never attaches credentials to an existing account on email equality alone.
  • Uniform responses for known/unknown emails (always 202), driver errors are never surfaced, starter pages ship a tight CSP, no-store, nosniff, and validate mount paths before interpolating them into HTML.
  • Authorization reads live grants every time (no stale roles in sessions), has no implicit admin/wildcard, scopes are exact, DB errors never become a grant, and suspended users are denied.

Findings

HighAnyone can lock a victim out of email-token login with one request per minute

auth/src/howdy/auth.gleam:181-221 (request_challenge)

Each token request (a) takes the 60-second per-email cooldown and (b) deletes every pending challenge for that email (DELETE … WHERE expires_at <= $1 OR email = $2). An attacker who POSTs /login with the victim's address once a minute permanently holds the cooldown, so the victim's own requests get 429, and any token the victim did manage to receive is invalidated by the attacker's next request. The victim also receives ~1,440 emails a day. The per-IP limiter (30/min) does not interfere with this at all.

Fix: do not invalidate older challenges on a new request — allow a small number (e.g. 3) of live challenges per email and delete only the oldest beyond that. Replace the flat cooldown with an escalating per-email budget (e.g. 3 per 15 min, 10 per day). Optionally bind the challenge to the requesting browser with a short-lived nonce cookie so only the requester can redeem it, which also blunts "read me the code" phishing.

HighRate limiting is keyed on socket IP with no way to configure it

auth/src/howdy/auth/routes.gleam:26,65

api() hard-codes rate_limit.by_ip at 30 requests/minute. Howdy's own docs say that behind a proxy every request shares the proxy's IP — so in the most common production topology, all users share one 30/min bucket and a single client can take auth down for everyone. The limiter also covers GET /me and /logout, so an SPA that calls /me on navigation, or an office behind NAT, will hit 429 in normal use.

Fix: accept the limiter/key function as an argument (routes.api(identity, at:, limit_by:)), defaulting to by_ip. Apply the strict limiter only to the unauthenticated credential endpoints and a much looser one (or none) to /me and /logout.

MediumNo password lifecycle: change, reset, or add-to-existing-account

auth/src/howdy/auth.gleam:307-315 — the only INSERT INTO howdy_auth_passwords

A password can only be set during registration. A user who forgets it can still sign in by email token but can never replace the password; a user who suspects compromise cannot rotate it; an email-only user cannot add one. For a security module, "cannot rotate a compromised credential" is a real gap, not just a missing feature.

Fix: add set_password(auth, principal, new_password) requiring a recently created session (email-token exchange within N minutes acts as the reset proof), which upserts the hash, revokes all other sessions, and writes an event.

MediumPassword-attempt throttle enables targeted lockout and never escalates

auth/src/howdy/auth.gleam:414-437

Five attempts per email per minute, counted before verification and shared globally. Six junk requests a minute lock the real user out of password login indefinitely (email-token login is the only fallback — and see the first finding). Conversely the window never grows, so a patient attacker gets 7,200 guesses/day per account forever. The 15-character minimum makes online guessing impractical, but credential stuffing with reused long passwords still works at that rate.

Fix: throttle on the pair (email, client key) first and on email alone with a much higher ceiling; use exponential back-off on consecutive failures; reset on success; record failures as events so they can be alerted on.

MediumAudit trail is too thin to investigate an incident

auth/src/howdy/auth.gleam:589-605 · auth/src/howdy/authorization.gleam:72,92,111

Events record only user_id, a free-text action and a timestamp. There is no actor (who suspended whom? who granted the role?), no client IP/user agent, and failed logins / failed exchanges are never recorded (they return before or roll back the event). Role events pack data into the action string ("role.assigned:org:42:admin") and define_role writes an empty user_id. The table has no index and no retention, so it also grows without bound.

Fix: add actor_id, subject/detail columns and an (user_id, occurred_at) index; make privileged functions take the acting Principal; log failures in a separate committed write (as the attempt counter already does); expose a prune_events(before:) helper.

MediumSessions are fixed 24 h bearer secrets with no management

auth/src/howdy/auth.gleam:50,319-340

No idle timeout, no sliding renewal (active users are logged out mid-work at 24 h), no way for a user to list or revoke their other sessions, and no metadata (created-at, last-seen, user agent) to make such a list meaningful. Lifetime is a const, so an app wanting 1 h admin sessions or 30 d consumer sessions must fork.

Fix: make lifetime and idle timeout configurable on Auth; store created_at/last_seen_at; add sessions(auth, principal) and revoke_session.

LowA failed exchange does not burn the token

auth/src/howdy/auth.gleam:267-317

The consuming DELETE … RETURNING is inside the same transaction as account checks. If a later step fails (account exists, user suspended, registration disabled, passwords disabled) the rollback restores the challenge, which stays redeemable until it expires. Not exploitable given 256-bit tokens, but it contradicts the "single-use" promise in the docs and UI.

Fix: consume the challenge in its own committed transaction, then do the account work in a second one.

LowOrigin validation accepts values a browser will never send

auth/src/howdy/auth.gleam:111-138

https://Example.com, https://example.com:443 and http://localhost:80 all pass validate_origin, but browsers serialise the Origin lower-cased with default ports removed, so every cookie write would then fail with 403 — a confusing fail-closed misconfiguration. Some("::1") without brackets is also unreachable.

Fix: canonicalise at construction (lower-case host, strip default port) or reject non-canonical input with a specific error.

LowSmaller hardening items

• Session and Delivery are public records with a plaintext token field — one echo/string.inspect in application code leaks a credential. Consider an opaque Secret wrapper with an explicit reveal.
• No breached/common-password check and no Unicode normalisation (NIST 800-63B recommends both; without NFKC the same password typed on a different OS can fail).
• No rehash-on-login path, so raising Argon2 cost later will not upgrade existing hashes.
• Throttle keys are unsalted SHA-256 of the email — that is not meaningful pseudonymisation (and the challenges table stores the plaintext email anyway); either drop the digest or HMAC with a server key.
• Registering with an address that already has an account still delivers a token that then fails at exchange with a bare 401. Give Delivery an AlreadyRegistered intent so the app can send a "you already have an account" email instead.
• users.email and identities.subject duplicate the address; token login reads one and password login reads the other. The day email-change lands, these can diverge.

Maintainability — 7 / 10

What is done well

  • Clear layering: headless operations (auth) → HTTP transport (routes) → optional UI (pages), with storage, hashing, tokens and schema under internal/. Authorization is a separate module with a separate migration package.
  • Opaque Auth/Authorization/Passwords types with builder-style opt-ins (allow_registration, with_passwords) — secure defaults are the path of least resistance.
  • Comments explain why, not what (cooldown committed before hashing, write-lock promotion on SQLite, mailbox trick for typed rollback errors, requester ID in the global lock). This is the kind of commentary that saves the next maintainer hours.
  • 36 tests, run in CI against both SQLite and a real Postgres 17, including concurrency, rollback, schema drift, migration races, a corrupt-hash fail-closed test, and an Argon2 known-answer vector.
  • Immutable, checksummed, append-only migrations with an advisory lock; a thorough README (375 lines) and a runnable example.

Findings

HighVendored, patched Argon2 C sources are a long-term liability

auth/vendor/jargon/ · auth/gleam.toml:16

The fix is correct and well documented, but the package now owns ~4,000 lines of C crypto, needs a manual make before every build, cannot be published to Hex (path dependency), and the README states that no upstream issue has been filed — so nothing will ever make this go away. The vendored copy also has no recorded checksum against the Hex tarball, so a reviewer cannot cheaply confirm "only one constant changed". (Minor: the Makefile lists ref.ci; it only works because basename strips the suffix.)

Fix: file the upstream issue/PR against Pevensie/jargon now and link it in the README; commit a PATCH.diff plus the upstream tarball SHA-256; add a CI step that diffs vendor against upstream. Note that existing hashes produced by buggy upstream builds are incompatible — worth stating in the migration notes.

MediumAll policy is hard-coded

auth.gleam (60, 600, 86_400, 5/6, 1024, 43) · routes.gleam (30/60, 4096) · password.gleam (15)

Session length, challenge TTL, cooldown, attempt limits, body limits and password minimum are magic numbers scattered through SQL parameters and conditionals; two of them (60 in the cooldown and in TooManyRequests(60); 5 vs 6 in the attempt SQL and the guard) must be changed in lock-step. Every consumer who needs a different value has to fork.

Fix: a single Policy record with named defaults held inside Auth, plus with_session_seconds-style setters. Name the remaining constants.

MediumSchema fingerprinting is brittle with no escape hatch

auth/src/howdy/migration.gleam:161-235

Startup refuses to run if a digest of catalog output changes. That output is not a stable interface: pg_get_constraintdef/pg_get_indexdef formatting can change between Postgres majors, polroles are cluster-specific OIDs, attnum changes after dump/restore of a table with dropped columns, and it depends on current_schema()/search_path. A routine PG upgrade or restore could leave an app unable to boot with "schema was changed outside its migrations" and no supported way to recover except editing the ledger by hand. It also forbids legitimate DBA actions such as adding an index to a hot auth table.

Fix: add an explicit migration.rebaseline(repo, package) operator command; consider fingerprinting a normalised structural subset (tables, columns, types, nullability, constraints) rather than rendered definitions, and make extra indexes a warning rather than fatal.

MediumStringly-typed and boolean-flag code in places that matter

• exchange matches the stored intent as "register" -> … | _ -> Ok(Nil) (auth.gleam:292) — add a decoder back to Intent so an unknown value fails instead of silently meaning "login".
• authorization.check(…, permission: Bool) and pages.page(…, register: Bool, password: Bool) are flag parameters; call sites read page(identity, prefix, api, True, False). Use small custom types (Role | Permission, Page variants).
• Adapter dispatch is case repo.adapter_name(repo) { "postgres" … _ -> sqlite } in four places with inconsistent fall-through: connect rejects unknown adapters while lock_user, lock_migrations and fingerprint silently treat them as SQLite. Parse once into a Backend type.

LowStructure and readability

• auth.gleam is 605 lines mixing configuration, validation, five flows and admin operations, with 200-character inline SQL strings. Move statements into an internal/queries module with named functions; it makes the flows readable and the SQL auditable in one place.
• The SQLite write-lock promotion (UPDATE … WHERE 1 = 0) appears twice as a copy-pasted trick — wrap it as db.write_transaction.
• suspend, resume, assign, revoke succeed silently for a non-existent user/role (assign relies on an FK error surfacing as a generic 500). Return NotFound.
• The package defines howdy/migration, howdy/auth and howdy/authorization inside the core package's module namespace. BEAM module names are global, so if core ever adds howdy/migration the two packages cannot coexist. Consider howdy_auth/… or at least reserve the names in core.
• The generic migration runner is useful beyond auth — it arguably belongs in its own package rather than being owned by the auth module.
• One 1,038-line test file with names like session_expiry_logout_and_suspension_test covering several behaviours each; when one fails it is unclear which. Split by area and into one behaviour per test.
• HTML is built by string concatenation. It is safe today (inputs are validated), but every future edit carries injection risk; a tiny escaping helper or an HTML builder would make that structural.

What is done well

  • Authenticating a request on Postgres is one primary-key lookup with a PK join; a permission check is one more indexed query. No N+1, no per-request hashing (SHA-256 only).
  • Expensive hashing is deliberately kept outside transactions and outside the SQLite lock, so it never holds a connection or blocks other requests.
  • The NIF is flagged ERL_NIF_DIRTY_JOB_CPU_BOUND; memory cost per hash is bounded (19 MiB) and the IP limiter caps concurrent abuse.
  • Throttles use single-statement upserts — atomic without explicit row locks — and expired rows are reaped opportunistically, so no background job is needed.

Findings

HighSQLite mode serialises every auth operation behind global:trans

auth/src/howdy_auth_ffi.erl:7-8 · auth/src/howdy/auth/internal/database.gleam:19-28

Every call — including the read-only authenticate and allowed on every authenticated request — takes a global lock. global is designed for rare cluster-wide coordination: each acquire is a round-trip to the global_name_server process, and a contended acquire does not queue, it sleeps a random, exponentially growing interval (up to 8 s) and retries. In the benchmark above, eight concurrent callers holding the lock for 1 ms produced a worst-case wait of 2.9 s. It is also unfair, so a request can starve. Under modest concurrent traffic this becomes sporadic multi-second page loads.

Fix: replace it with a per-Repo serialiser process (a tiny actor/gen_server that runs the closure, giving FIFO fairness and microsecond hand-off), or better, push the serialisation into Gloo's SQLite adapter where it belongs. With WAL mode, reads need no lock at all if a second read-only connection is used.

MediumNo caching on the per-request path

auth/src/howdy/auth.gleam:478-492 · auth/src/howdy/authorization.gleam:135-157

A guarded route with a permission check costs two DB round-trips (plus two lock acquisitions on SQLite) before the handler starts. Always-fresh reads are a defensible security choice, but there is no option for apps that would trade 5 s of staleness for halving DB load.

Fix: offer a single-query authenticate_and_check joining sessions→users→assignments→permissions, and/or an optional short-TTL ETS cache keyed by session digest that logout/suspend/revoke invalidate.

MediumMissing indexes and scan-prone cleanup queries

auth/src/howdy/auth/internal/schema.gleam

• DELETE FROM howdy_auth_challenges WHERE expires_at <= $1 OR email = $2 — there is no index on email, and an OR across two columns usually defeats the expiry index too; split into two statements and index email.
• howdy_auth_throttles(next_at) and howdy_auth_password_attempts(window_start) are swept on every request without an index. They are small in normal use but these are precisely the tables an attacker inflates (one row per distinct email), turning every login into a sequential scan when you can least afford it.
• FK columns without indexes: howdy_auth_identities(user_id) and howdy_authz_assignments(scope, role) — cascading deletes of a user or role scan the child table on Postgres.
• howdy_auth_events has no secondary index and no retention.

LowSmaller items

• The Argon2 build compiles the portable ref.c, not the SIMD opt.c. Defenders pay roughly 1.5–2× more per hash than necessary, which is budget that could otherwise buy a higher memory cost. Build opt.c on x86-64 when available.
• Each issue_session also runs an expired-session sweep inside the login transaction; on a large table after quiet periods that is a long delete holding the user row lock. Bound it (LIMIT via subquery) or sweep out of band.
• define_role inserts permissions one statement at a time; fine for tens, slow for hundreds — use a multi-row insert.
• /client.js is served no-store; it is a static constant and could carry an ETag or long max-age with a versioned path.
• 43-character random text primary keys for users are larger and less index-friendly than UUIDv7; irrelevant at small scale, noticeable in every FK and index at large scale.
• No concurrency cap on in-flight Argon2 jobs: N simultaneous password requests allocate N × 19 MiB and saturate the dirty schedulers (shared with all other NIF work). A small semaphore would make the worst case explicit.

Observations at that review

The first two observations are addressed by the latest correction pass; they are preserved here as the original finding descriptions.

LowThe authorization cache is invalidated by every auth transaction, not just the ones that change grants

auth/src/howdy/auth/internal/database.gleam:55,66

db.transaction bumps the single global generation twice, and logins, token requests, logouts and password attempts all run through it. It is safe — it can only cause extra reads — but on a busy site the cache is flushed every time anyone signs in, so the hit rate will be far below what the TTL suggests, which is precisely when the cache is wanted.

Fix: invalidate only from the operations that can change an answer: define_role, assign, revoke, suspend, resume. Minor related points: the cache key embeds the full SQL text (a Role/Permission tag would do), and the generation restarts at 0 if the lock server is ever restarted — harmless given the 60 s TTL ceiling, but a erlang:unique_integer seed would remove the question.

LowA wrong, non-NFC password costs two Argon2 verifications

auth/src/howdy/auth/internal/password.gleam:91-105

The legacy fallback doubles the work for that input class. It is bounded by the per-client back-off, so this is a note rather than a risk; remove the fallback once legacy hashes have aged out.

LowStill open

The address-keyed email-token throttle trade-off (a third party can delay an owner’s new requests; documented, not changed); the vendored Jargon copy pending Pevensie/jargon#9; auth.gleam has grown to ~810 lines and would split naturally into password, session and administration modules; the actual GitHub Actions workflow has not been run from here.
